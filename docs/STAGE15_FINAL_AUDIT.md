В изученном исходном коде не обнаружена подтверждённая блокирующая ошибка формулы спреда, сопоставления рынков, проверки свежести котировок или основного цикла. Эти компоненты не переписывались без основания. Автоматические тесты и проверки из CI уже выполнялись на исходном дереве Stage 14 непосредственно перед слиянием в `main`; результат workflow — успешный: [GitHub Actions run 39389856549](https://github.com/Quantum103/scrinner/actions/runs/39389856549).

Локальный запуск команд из этого окружения выполнить не удалось: клонирование репозитория остановилось на ошибке DNS при доступе к `github.com`. Поэтому ниже чётко разделены результаты CI, анализ исходников и внешние проверки, которые реально не удалось выполнить.

## Что проверено в коде

- **Конфигурация и запуск:** `go.mod` требует Go 1.26.0. Конфигурация загружается и валидируется до открытия базы и создания цикла сканирования. Обязательные настройки, интервалы, срок актуальности, порог спреда, неизвестные активированные биржи и URL OKX/Gate проверяются явно.
- **Поток данных:** `configuredAdapters` подключает только включённые YAML-адаптеры. Рынки нормализуются по структурированным полям; исходный биржевой `Symbol` сохраняется. Котировки сопоставляются с рынками того же адаптера, повторные/невалидные котировки отбрасываются. Сохраняются снимки, а детектор обрабатывает только сохранённые актуальные снимки.
- **Расчёт возможностей:** используется Ask для покупки и Bid для продажи. Порог проверяется десятичной арифметикой без округления до сравнения. Межбиржевые пары одной биржи исключаются. Spot и Perpetual разделены в модели рынка, но могут сопоставляться между собой для одного базового актива. Детектор поддерживает Spot→Spot, Spot→Perpetual, Perpetual→Spot и Perpetual→Perpetual.
- **Свежесть:** `Ticker.IsFresh` требует валидные положительные цены, локальное время получения, актуальность основной временной метки и актуальность отдельной биржевой метки, когда она предоставлена. Будущее время, отсутствие времени получения и превышение `max_data_age` отклоняются. Для сопоставления котировок проверяется временной разрыв.
- **Цикл:** циклы не накладываются друг на друга; сбор бирж ограничен параллелизмом до шести адаптеров; ошибки отдельных бирж отражаются как частичный или неудачный результат. Следующий запуск ожидает интервал после завершения предыдущего. Отмена контекста и системные сигналы завершения обрабатываются.
- **История:** цены и спреды хранятся как decimal-строки; пакетные записи используют транзакции. Поток статистики фильтрует период по полуинтервалу [since, until), повторно проверяет временные границы и валидность наблюдений.
- **Резервное копирование:** `db-check` использует чтение без миграций; `backup` использует SQLite `VACUUM INTO`, проверяет копию и исходную базу и защищает существующий файл от перезаписи без явного `--force`. WAL/SHM-файлы работающей базы не удаляются.
- **Границы безопасности:** изученные адаптеры используют публичные REST-данные, не требуют торговых ключей и не содержат вызовов размещения ордеров или перевода средств. Валовой спред не равен гарантированной или чистой прибыли.

## Шесть адаптеров

У каждого адаптера существуют отдельные тесты метаданных и пакетных тикеров с контролируемыми ответами API:

| Биржа | Проверенные по коду правила |
|---|---|
| Binance | Активный Spot USDT; USDⓈ-M Perpetual с USDT quote/margin; пакетные bid/ask; Spot/Futures раздельно |
| Bybit | Spot и Linear Perpetual; quote/settle USDT; проверка категории, ответа API и пагинации |
| MEXC | Структурированные Spot-поля, доступность обеих сторон торговли; USDT perpetual и состояние контракта |
| OKX | Spot USDT/live; линейные SWAP с расчётом в USDT; согласованность instId и метаданных |
| Gate | Торгуемые обычные Spot USDT; исключение ETF и делистинга; фильтрация USDT perpetual |
| Bitget | Структурированные активы, статус и классификаторы инструмента; delivery и специальные инструменты исключаются |

Клиенты используют ограниченные таймауты, закрывают HTTP response body, поддерживают отмену контекста и ограниченное число повторов. В исходниках также есть проверки ошибок HTTP и прикладных кодов API. Компиляция сама по себе не считается подтверждением реального доступа к бирже.

## Внешние API и пределы проверки

Прямые живые запросы ко всем шести публичным API из текущего окружения выполнить и надёжно подтвердить не удалось. Репозиторий невозможно было клонировать из-за DNS-ошибки, а доступные веб-ответы API оказались кэшированными и не доказывают текущую доступность. Поэтому ни одну биржу в этом отчёте нельзя считать прошедшей живую проверку на момент аудита. Это ограничение внешней проверки, а не доказанная ошибка адаптера. Тесты адаптеров используют локальные контролируемые ответы.

## История, статистика и восстановление

- Статистика рассчитывает пороги 1%, 2% и 3%, наблюдения, уникальные направленные возможности, эпизоды, среднее/максимальное значение, длительности, активы, маршруты Spot/Perpetual и распределение по часу. Эпизоды выводятся только из сохранённых положительных наблюдений, поэтому реальные интервалы, когда возможность возникала и исчезала между циклами, неизвестны.
- Наблюдения без `cycle_id`, сохранённые до журналирования циклов, не позволяют восстановить исходный порог обнаружения и периоды отказа/простоя. Отчёт помечает такую историю как неполную; недостающие значения не синтезируются.
- Автоматическая команда `restore` в коде не реализована. Есть создание, проверка резервной копии и проверка базы. Безопасное восстановление выполняется отдельно: проверить копию, сохранить исходный файл, затем запускать приложение с путём к отдельному восстановленному файлу. Не заменять активную базу и не удалять вручную `-wal`/`-shm`.
- В репозитории хранится старая fixture `data/arbitrage.db`, которая может не содержать `scan_cycles`. `doctor` намеренно не мигрирует базу и сообщает о несовместимости; обычный запуск приложения применяет миграции. Для диагностики старой базы безопаснее сначала работать с копией.
